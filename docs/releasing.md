# リリース手順

## バージョン

初期開発は `0.y.z` を使用します。0.x は安定 API の約束ではありません。プロジェクト内の運用として、機能・マイルストーンは minor、既存機能の修正は patch を上げます。破壊的変更は 0.x でもリリースノートに明記します。

試験版には `v0.1.0-alpha.1` のような prerelease を使えます。`package.json` に 0.1.0 があるだけではリリース済みを意味しません。公開 API と互換性の約束を定めてから 1.0.0 を検討します。

## 通常リリース

1. 所有者から対象範囲とリリース実行の承認を得る。
2. 対象 Issue、変更点、既知の制約、必要なら移行・復旧手順をまとめる。
3. 作業ブランチから `develop` にバージョンと `CHANGELOG.md` の更新を PR で統合する。package と lock のバージョンをそろえる。
4. `develop` → `main` の release PR を作る。CI と必要な手動試験を確認する。
5. **merge commit** で統合し、実際の main のコミットにタグを付ける。リリース PR を squash しない。
6. 同じタグで GitHub Release を作り、試験版なら prerelease を明示する。対象 Issue を閉じる。
7. main にのみ入った変更があれば develop に戻し、差分を確認する。main/develop は削除しない。

## 緊急修正

`main` から `hotfix/<issue>-<summary>` を切り、PR と CI を通して main へ統合します。修正は PR で develop にも戻します。タグの付け直しや公開済み履歴の書き換えで修正しません。

## 注意

ソースコードのリリースとサービスのデプロイは別です。このリポジトリに自動デプロイや自動リリースはありません。安定化作業と次の開発を並行する必要が生じるまでは `release/*` ブランチを増やしません。
